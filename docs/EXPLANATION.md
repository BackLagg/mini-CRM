# Как устроена система (для руководителя)

## Зачем это нужно

Это небольшая система для строительной компании: руководитель (постановщик) создаёт **объекты** — стройки с названием и адресом — и ставит на них **задачи**. Исполнители видят только свои задачи, выполняют их и отправляют на проверку. Постановщик принимает работу или возвращает на доработку с комментарием.

## Роли

**Постановщик** может создавать, менять и удалять объекты и задачи, назначать исполнителя, принимать или возвращать задачи. Видит все объекты и задачи.

**Исполнитель** видит только задачи, где он назначен исполнителем, и объекты, на которых такие задачи есть. Может перевести задачу «в работу», «на проверку» или снова «в работу» после доработки. Не может читать чужие задачи и не может менять текст задачи или назначение — только смену статуса по правилам.

## Жизнь задачи

Статусы: **Новая** → **В работе** → **На проверке** → **Принята** или **На доработке** → снова **В работе**. Другие переходы запрещены. При возврате на доработку комментарий обязателен.

Каждая смена статуса и каждое изменение полей постановщиком (название, описание, исполнитель, объект) записывается в **историю** в карточке задачи.

## Как защищены данные

Правила доступа заданы **в базе данных** (Supabase/PostgreSQL), а не только кнопками в интерфейсе. Даже при прямом обращении к API исполнитель не получит чужие задачи. Смена статуса проверяется специальной функцией в базе; запрещённый переход не выполнится. Записи истории нельзя подделать или удалить через обычный доступ приложения.

Регистрация новых пользователей в системе отключена; тестовые аккаунты создаются администратором в Supabase. Секретные ключи сервера не хранятся в коде сайта и не попадают в репозиторий.

## Что исполнитель не может сделать

- Посмотреть задачи других исполнителей или объекты, где у него нет задач.
- Изменить название, описание или исполнителя задачи.
- Принять задачу или отправить на доработку (это делает постановщик).
- Обойти цепочку статусов (например, сразу «принять» новую задачу).
